# HANDOFF Addendum — Finding IDs, Schema Contract, Remediation Engine

Appends to HANDOFF.md. Covers everything added on top of the original scan pipeline: stable finding IDs, the Pydantic response contract, and the remediation engine wired into /scan and /remediate.

## 1. Stable Finding IDs

backend/services/scan_service.py now generates a finding_id for every finding:

finding_id = sha256(resource_id | resource_type | category | finding)[:16]

Why: one resource (e.g. a single S3 bucket) can produce multiple distinct findings, so resource_id alone isn't a valid key. Any downstream table (risk scores, findings history, etc.) should key off finding_id, not resource_id.

finding_id is attached in two places:
- run_full_scan() — used by GET /scan
- _run_scanner() in main.py — used by each GET /scan/<service> route

## 2. Response Schema Contract (backend/models.py)

All scan endpoints now validate against Pydantic models instead of a hand-copied JSON example in docs:

- Finding — finding_id, resource_id, resource_type, finding, severity, category, evidence, status, remediation (optional)
- RemediationPlan — kind, description, risk (optional)
- ScanError — scanner, error
- ScanResult — full /scan response (total_findings, severity_summary, findings, errors)
- SingleScannerResult — per-service response (findings, errors)

resource_type, severity, category, status, and remediation.kind are all Literal types — invalid values will fail validation and show up as a 500 rather than silently passing bad data downstream. Build against these field names directly; they're visible and enforced in /docs.

## 3. Remediation Engine (backend/services/aws/remediation.py)

Every finding returned by /scan and /scan/<service> now carries a remediation plan, generated by plan_remediation(finding). Plans have one of three kinds:

- automatable — safe to apply via POST /remediate with confirm: true
- manual_action_required — needs a human to act outside the API (console, code review, etc.)
- no_action_needed — finding is already resolved / not a real issue

### Currently automatable

S3 (resource_type: s3_bucket):
- Block Public Access disabled -> enables it
- Bucket publicly accessible -> resets ACL to private
- Versioning disabled -> enables versioning
- Encryption disabled -> enables default SSE-S3 (AES256)

IAM (resource_type: iam_account):
- Weak password policy -> updates to length >=14, symbols, numbers, mixed case
- Access keys older than 90 days -> deactivates them

### Currently manual-only (never auto-applied, even with confirm: true)

- Root account MFA (must be enabled in the AWS console — no API for this)
- Per-user MFA enrollment (only the user can do this)
- Wildcard (Action:*/Resource:*) IAM permissions — too high-risk to auto-revoke; could break live workloads
- EC2 (security groups), CloudTrail, and Lambda findings — no scanner-specific remediation logic exists yet. These currently fall through to a generic manual_action_required default so they're still flagged for review rather than silently skipped. Next step: wire these into remediation.py once their finding shapes are finalized.

### Known limitation

The S3 "publicly accessible" fix only resets the bucket ACL. It does not inspect or modify bucket policies, which can also grant public access independently of ACLs. A bucket could still be public after this fix runs if the exposure is coming from its policy rather than its ACL.

## 4. /remediate Safety Model

POST /remediate is the single approval gate for applying any fix:

1. Requires confirm: true — returns 400 otherwise.
2. Re-runs plan_remediation() on the submitted finding — if it isn't automatable, returns 422 and does nothing, regardless of confirm.
3. Only then calls apply_remediation() and returns the result (502 if the underlying AWS call fails).

There is no autonomous or scheduled remediation. Findings are only detected and labeled by /scan; nothing is ever changed in the AWS account until a specific finding is explicitly submitted to /remediate with confirm: true. This is a one-fix-per-explicit-request model, not an auto-heal loop.
